# TrailLedger — experience and visual direction

## Design thesis

Lead with the research question and supporting evidence. A user should be able to travel from a claim to the exact run, data transformation, and trial history that support it.

## Screen model

| Screen / surface | Primary task | Interaction and state |
| --- | --- | --- |
| Research index | Find a hypothesis and its state | Show registered, exploratory, amended, and withdrawn claims |
| Result ancestry | Inspect dependencies | Select a node to open hashes, availability, and transform meaning |
| Trial comparison | Review the full search | Show failed and interrupted attempts alongside favorable outcomes |
| Reproduction desk | Verify a bundle | Separate missing input, integrity failure, environment mismatch, and numerical disagreement |

## Visual system

The repository identity uses forest green, mint lineage edges, document-like report typography, and compact experiment tables with persistent identifiers. The application should develop this direction with readable typography and deliberate information hierarchy. Numbers align by scale and unit. Visual emphasis belongs to the active question, selected event, unresolved discrepancy, or next action. Avoid filling the opening view with interchangeable statistic cards.

## Interaction rules

Selection persists when the user changes a filter, or the UI explains why the selected object is now outside the view. Comparisons preserve each run's identity and configuration. Loading, empty, incomplete, invalid, stale, and successful states are distinct. A result panel keeps the evidence drawer available so the user can inspect source events without losing context.

Keyboard navigation covers the primary journey. Color is reinforced by text, symbols, or line patterns. Tooltips expand unfamiliar terms but do not hide required units or failure reasons. Text and chart axes remain readable at normal laptop sizes. Destructive local edits provide a review of their exact scope and preserve recoverable prior revisions where feasible.

## First demonstration storyboard

Register a question; run several synthetic trials including one deliberate failure; inspect a favorable result; change the input under the same filename; show the new lineage; export and verify a bundle in a clean workspace.

The first demo uses synthetic or explicitly redistributable material and carries an illustrative label until the runtime produces it. The committed SVG banner is an identity asset, not evidence of a working application. Future screenshots should come from the application at a recorded revision.
